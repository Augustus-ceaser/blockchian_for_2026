# Phase 5.4–5.6 Web3 本地路演手册

本手册对应 `blockchian_for_2026` 的本地集成演示：Phase 5.4 链上四方确认、Phase 5.5 钱包身份与角色资格、Phase 5.6 演示币托管和双证明自动结算。

> **演示边界**：这是一次性 Hardhat 本地链上的工程原型。SBT 不是法定 KYC、医疗资质或机构尽调；合约未经过独立安全审计；`mCNY` 没有真实价值；不得接入主网、真实资金、患者数据或生产业务。

## 1. 启动前准备

需要：

- Docker Desktop 已正常运行；
- Node.js、pnpm、后端与前端依赖已按项目原有说明安装；
- 仓库根目录已存在 Git 忽略的 `config/phase4-demo.env`，其中本地资产路径和四个演示账号密码均已配置；
- 浏览器安装支持 EIP-1193 的钱包扩展，并为四个角色准备四个相互隔离的浏览器 Profile；
- `blockchain/node_modules` 已安装。首次使用时执行：

```powershell
cd "D:\罗小罗\blockchian_for_2026\blockchain"
pnpm install --frozen-lockfile
pnpm build
pnpm test
```

不要把钱包私钥、助记词、API Key 或演示密码写进文档、截图、录屏、Git 提交或聊天记录。

在仓库根目录运行：

```powershell

.\scripts\prepare_web3_roadshow.ps1 -Open
```

脚本依次完成：

1. 停止本仓库上一次记录的本地链进程；
2. 在 `127.0.0.1:8545` 启动隐藏的 Hardhat 节点（Chain ID `31337`）；
3. 部署角色凭证、合约登记、演示结算币和托管合约；
4. 校验并生成 Git 忽略的 `blockchain/deployments/localhost.json`；

7. 检查服务状态，并打开路演入口。

**注意：每次运行都会重建 `medtrust_phase4_demo` 专用演示库，上一轮演示产生的钱包绑定、合约、订单和结果会被清除；它不会重置其他数据库。**

## 4. 推荐演示顺序

### 4.1 Phase 5.5：绑定钱包并取得角色资格

1. 分别用四个网站账号登录四个浏览器 Profile。
2. 在右上角打开“钱包与资格”。
3. 每个角色连接与清单一致的钱包，点击“连接钱包并签名绑定”。服务端从当前网站账号推导机构和角色，前端不能自行选择角色。
4. 清洁部署中，运营账号会先显示待签发。在运营账号自己的“钱包与资格”面板点击“初始化本地运营资格”；后端仅在 `local + Chain ID 31337` 下，核对当前登录角色、钱包所有权、部署清单中的运营/发行地址和 Hardhat 解锁账户后代发交易，再以可信 RPC 复核 `CredentialIssued`。生产或局域网模式不会提供这个入口。
5. 运营端再次用运营钱包完成管理会话签名，查看待签发队列，逐一点击“签发链上资格”。
6. 返回各角色窗口刷新，确认状态为“资格有效”，并检查钱包地址、角色、Token ID 和有效期。
7. 可退出网站后，用“钱包签名登录”验证后续登录；签名只证明地址控制权，实际账号、机构和角色仍由服务端的已审核绑定决定。

链上凭证是不可转让、可撤销、可过期的 ERC-5192 风格角色声明。链上仅保存 DID、机构、角色和审核证据的摘要，不保存身份证明材料。

### 4.2 Phase 5.4：数字合约四方确认与生效

前提是已有一条完成业务审批、进入 `proposed` 状态的固定数字合约，并且四方钱包资格都有效。

1. 运营端打开该合约详情，在“链上四方确认”卡片点击“登记链上摘要”。
2. 需求方核对同一摘要和条款，勾选确认后点击“钱包确认”。
3. 医院数据方以自己的钱包完成确认。
4. 模型提供方以自己的钱包完成确认。
5. 空间运营方最后确认。合约强制运营方在前三方之后签署，进度应从 `0/4` 到 `4/4`。
6. 如果有效期已经开始，第 4 次确认会在同一交易中自动触发生效；如果尚未到 `validFrom`，到期后使用“触发链上生效”。
7. 刷新并检查登记交易、生效交易、摘要和 `active` 状态均已被后端可信 RPC 复核。

这是固定业务四方的 `4-of-4` 状态机，不是通用 DAO，也没有部署 Safe 等通用多签钱包。当前端到端流程只支持一次性 EOA；接入 Safe 前还必须实现 EIP-1271 验签和 Safe 内部调用回执核验，不能直接把参与方地址换成 Safe。

### 4.3 Phase 5.6：托管、受控执行、审核与自动结算

1. 需求方完成服务申请审批和服务协议确认，进入订单结算页。
2. 不选择普通“模拟支付”，改选“链上演示托管”。
3. 需求方钱包依次签署演示 `mCNY` 的精确额度授权和 `openEscrow` 交易。
4. 等待后端通过配置的 RPC 复核 `EscrowFunded`，页面应显示“资金已托管，待执行”。浏览器回执只用于定位日志，不能自行决定付款成功。
5. 按原有业务流程完成执行准备和受控计算，确保仅有一条符合订单的成功运行，并且完成回执已落库；原始 Artifact 必须继续保持隔离。
6. 完成原有多方结果审核，并由平台生成获批的安全结果包。付款不替代结果审核，Phase 5.6 不能绕过这一门槛。
7. 空间运营方返回同一订单结算页，点击“运行独立证明并自动结算”。本地后端只从数据库中的成功运行、隔离 Artifact 和获批结果包生成摘要，并让两个不同的本地证明账户分别提交执行证明与交付证明。
8. 刷新后确认两项证明均已核验，托管状态为已结算；切回需求方结果页，此时一次性下载授权才会解锁。

双证明齐备时，合约自动把数据费、模型费和平台费计入三个收款地址的 `claimable` 余额。为避免某一收款方阻塞整体结算，实际代币领取采用单独的 pull-payment 提现；当前网站演示的是“结算权益已生成”，不应讲成真实法币已经到账。

这里的“自动交付”是：获批结果包的摘要与审核证据被交付证明锁定，合约自动结算后，网站才允许需求方创建一次性短期下载授权。结果文件始终由链下服务交付；它不是把患者数据、原始模型或结果文件写到链上，也不会绕过 Phase 5.7 审核。

若交付的是获批数据副本或模型许可，实际文件、模型权重和下载授权仍由链下服务按合同及审核结果发放；链上只记录摘要和结算状态。

## 5. 快速故障排查

| 现象 | 检查与处理 |
| --- | --- |
| 缺少 `config/phase4-demo.env` | 从 `config/phase4-demo.example.env` 复制到本地忽略文件，补齐本机资产路径和演示账号密码后重试。 |
| 提示缺少 blockchain dependencies | 在 `blockchain` 目录执行 `pnpm install --frozen-lockfile`，再运行 `pnpm build`、`pnpm test`。 |
| `8545` 被占用 | 先运行 `scripts/stop_web3_demo.ps1`；若仍占用，说明是未由本项目记录的进程，应先核对进程归属再停止，不要盲目结束系统进程。 |
| 网站账号返回 401 | 一键脚本重置后旧 Cookie 已失效；退出并使用本地配置密码重新登录。 |
| 看不到“钱包与资格”或提示 Web3 未启用 | 核对 `backend/.env.local` 已由一键脚本生成，后端已重启，并访问 `/api/v1/auth/wallet/capabilities` 检查能力状态。 |
| 钱包拒绝或网络不匹配 | 确认 Chain ID 为 `31337`，RPC 为 `127.0.0.1:8545`，当前地址与最新 manifest 的角色地址一致。 |
| 运营端看不到签发队列 | 清洁本地部署先在运营账号自己的“钱包与资格”中点击“初始化本地运营资格”，再完成一次运营钱包管理会话签名；若初始化按钮不出现，核对是否确为 `local + 31337` 且钱包与最新部署清单一致。 |
| 合约登记/确认按钮不可用 | 检查固定合约仍为 `proposed`、四方 SBT 未过期或撤销、钱包属于当前角色；运营方必须最后确认，且同一修订不能混用旧式签名和链上确认。 |
| 回执一直等待确认 | 点击页面的重新核验/刷新；检查 Hardhat 节点仍运行以及后端使用的合约地址与最新 manifest 一致。 |
| 无法建立托管 | 检查商业订单已确认协议、链上合约处于有效期内且为 `active`、需求钱包资格有效并使用正确账户。 |
| 自动结算按钮不可用或失败 | 必须使用运营端、本地链、已核验的托管订单；还必须恰好有一条成功运行和一个可用的获批结果包，并配置两个不同的证明账户。先完成结果审核，不要伪造证明。 |


如需同时停止原有路演应用进程，再执行：

```powershell

```

## 7. 上生产前仍缺少什么

- 至少一次独立智能合约安全审计、修复复审和可验证的审计版本摘要；
- 真实链选择、确认数与重组策略、RPC 冗余、链上事件索引和灾难恢复；
- HSM/MPC 或成熟多签的钱包密钥治理、角色撤销和紧急暂停流程；
- 真实支付机构、清结算、退款、税务、争议处理和监管合规；
- 独立执行证明服务与交付证明服务，禁止由平台运营账号同时扮演两种证明者；
- 法定身份、机构资质、授权链和隐私影响评估；
- 对链下结果、下载授权、合同正文和链上摘要之间一致性的正式验证；
- Safe/EIP-1271 合约钱包登录与内部调用回执识别；
- 生产级事件索引、重组回滚、业务键查链和持久 outbox。当前本地流程已能保存已广播交易哈希并恢复同一回执，但不应把它讲成已经解决了跨链与数据库的原子提交。
